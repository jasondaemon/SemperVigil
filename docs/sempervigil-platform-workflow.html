SemperVigil platform workflow and boundaries

This diagram is drawn from the SemperVigil docs, Helm layout, and runtime code paths. It models the documented public edge, the internal control plane, the worker lanes, and the storage / external-dependency boundaries. The public CDN box is labeled generically as Cloudflare / CloudFront edge to keep the diagram portable; the current docs identify Cloudflare as the live front door.

Database-orchestrated control plane Public traffic is edge-filtered before app services Runner pods claim control jobs, then spawn bounded worker passes Fetch uses a VPN sidecar for egress Build is dirty-state driven and publishes atomically

Solid arrows show internal state, queue, and file flow. Dashed arrows show outbound or external dependencies. The central database is the system of record for jobs, prompts, content, build state, and configuration.

1. Public ingress

External readers hit the CDN / edge proxy, then the internal security stack before reaching the public site service.

2. Control plane

The admin UI and orchestrator both read and write Postgres. The orchestrator decides when launch jobs and dirty builds should be admitted.

3. Fetch / enrich

Fetch runners claim control jobs, run bounded passes, fetch from sources through the VPN sidecar, and write articles, CVEs, and job state back to the database.

4. LLM lanes

LLM and OpenAI runners claim their queue lanes, resolve prompts and profiles from Postgres, and write structured enrichments back into the same system of record.

5. Build and publish

The build worker reads the data and site source PVCs, runs Hugo, and updates the release output that nginx serves as the public site.

Boundary notes
  • Public / Internet: untrusted browsers, readers, and crawlers.
  • CDN / Edge: Cloudflare / CloudFront label used for the public CDN front door.
  • Security tier: firewall, Traefik VIP, external-edge namespace, ModSecurity / CRS, and CrowdSec AppSec.
  • Internal control plane: admin, orchestrator, and Postgres.
  • Worker / data plane: fetch, llm_local, openai, build, and supporting services.
  • External dependencies: source sites, NVD / KEV, search backends, LLM providers, and VPN egress.
