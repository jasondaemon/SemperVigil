# Bounded autonomous v2 candidate

This source candidate is not deployed. Runtime stays 6065f8c and all v2 generation/scope controls remain off. No paid evaluation is performed by this implementation or its tests. The existing Microsoft/Astrana legacy pilot policy and contract module bytes are unchanged.

The normal scheduler calls the isolated v2 tick after the legacy tick. A default-off autonomous gate, explicit event scope, a fresh v2 cohort ID/token cap, an immutable generation pin and an expiring policy are required. Scope cannot overlap the configured legacy pilot, and its cohort ID cannot be reused. Existing event-source-report job queue, two-phase writer/reviewer, immutable source/call/projection lineage, approval admission role, promotion role, export and activation remain the authorities. No new database privileges, migration or endpoint is introduced.

## Configuration and accounting

`SV_EVENT_REPORT_V2_AUTONOMOUS=1` selects this candidate's normal path only alongside `SV_EVENT_REPORT_V2_ENABLED=1`, a nonempty `SV_EVENT_REPORT_V2_EVENT_IDS` list and `SV_EVENT_REPORT_V2_GENERATION_ENABLED=1`. `SV_EVENT_REPORT_V2_COHORT_ID` and `SV_EVENT_REPORT_V2_COHORT_TOKENS` define a fresh lifetime v2 cohort, with no fallback to legacy variables. Leave `SV_EVENT_SOURCE_REPORT_COHORT_ID`, `SV_EVENT_SOURCE_REPORT_COHORT_TOKENS` and `SV_EVENT_SOURCE_REPORT_PILOT_POLICY` unchanged for the Microsoft/Astrana pilot. The two policies may coexist only with disjoint scopes and distinct cohort IDs. `SV_EVENT_REPORT_V2_POLICY` is an exact JSON object with `starts_at`, `expires_at` (timezone-aware, window at most seven days), `max_runs` (1–100), `max_concurrent` (1–10, at most max_runs), `run_tokens` (1–200000, no more than cohort cap), `debounce_seconds` (0–86400), and `generator_version` (exact SHA256 returned by v2 configuration). No defaults authorize autonomous spending. Catalog SHA, retrieval, schemas, prompts, phase options and the new policy module are part of generation identity. Admission captures the complete policy separately in the immutable run snapshot. A separate captured code/catalog/options runtime identity lets restricted approval/promotion roles reject runtime drift without reading provider/model tables or acquiring new privileges. Distinct configured writer/reviewer model readiness is checked before admission; a default single-model configuration fails before transport.

Only successors with an actual qualified public predecessor, reconstructible baseline and meaningful evidence change can enter this cohort. No automatic initial backfill, generator-only refresh, analyst-question repair, correction allowance, pretransport retry rotation or arbitrary enrollment list is allowed. Exact snapshot/config repeats reuse the terminal run. A cohort advisory transaction lock serializes admissions across events; **each admitted run reserves its full lifetime run budget** against cohort capacity, including held/failed runs. Actual/reserved transport accounting and conservative payload reservation remain intact. Maximum run count and concurrent queued/running count apply independently. Unknown transport never automatically retries; a recorded provider budget overrun stops further cohort admission/publication. Provider compliance with completion caps is not a financial guarantee; overruns remain visible in raw usage.

Policy, expiry, generator/catalog identity, current complete sources and predecessor are checked before each transport phase. Approval admission and promotion independently verify the immutable policy, accepted whole-source review, zero outstanding reservation, exactly two completed phases with distinct writer/reviewer model names, evidence delta and native publication guards. An accepted result never itself changes the live site. Explicit editorial derivatives cannot be approved automatically. Published material remains readable after policy expiry or rollback; a disabled policy prevents new transport/approval/promotion, and stale candidates fail without changing the old public revision.

Verification does not acquire the capacity advisory lock: approval uses a separate connection, so locking in its caller would block itself. Capacity mutations remain serialized, snapshots are immutable, and the same policy/limits are revalidated by the approval/promotion authority. Normal role checks, event locks, predecessor compare, immutable qualification and revocation guard remain unchanged.

## Rollback and controlled later enablement

Before any later rollout, independently review the immutable code diff and complete tests. Keep current flags and pilot unchanged until its explicit retirement/expiry handling is agreed. A configured legacy pilot still prohibits scope overlap even after its timestamp expires: retire its policy deliberately rather than editing the active pilot or silently dropping limits. Use a new cohort ID and pin the candidate's actual deployed generation identity. Drain affected jobs and roll admission/generation/promotion processes together; ConfigMap edits do not change running process environments. Do not apply all unrelated platform manifests.

Rollback disables `SV_EVENT_REPORT_V2_AUTONOMOUS` and generation, drains/restarts relevant processes, and preserves cohort/run/call artifacts and the last qualified public revision. Admission capacity is never refunded or rotated to manufacture retries. A newer code/catalog generation requires a separately authorized fresh policy/cohort, not an in-place pin change. An already published revision is not withdrawn simply because its generation policy expired; source corrections/revocations continue through normal publication readers.
